# StyleGallery MCP·API 제품 조사

Understood as: 수익화 제품은 호스팅 MCP와 HTTP API로 정한다. 오른쪽 Fable 세션은 제품을 조사하고, 아래 Fable 세션은 자료·탐색 개선과 조사에서 도출한 로컬 제품 기반을 구현한다. 배포·결제·고객 연락은 실행하지 않는다.

확인일: 2026-09-19. 제품 방향은 사용자 결정이며, 수요·가격·수익성은 검증 전이다. 이 문서가 [이전 선택지 조사](2026-09-19-monetization.md)의 서비스형 파일럿 우선 제안을 대체한다. 공식 Anthropic Fable 5.1의 짧은 재조사 응답을 회수했고, 주 에이전트가 아래 공식 가격과 규격·로컬 코드를 재대조했다. 원래 긴 보고서의 출력 실패와 작업 상태는 [작업 대장](2026-09-19-execution-ledger.md)에 남긴다.

갱신: 2026-09-21. 사용자가 무료·유료 경계를 다시 정했다. **공개 corpus는 로컬과 원격 모두 무료로 두고, 유료 자료는 `site-compiler`로 실제 웹사이트를 관찰·전사한 사이트팩으로 한정한다.** 이 갱신은 아래 "제품과 고객", "무료·유료 경계와 가격 가설", "사이트팩 경계 조건", "출시 전 검증과 남은 결정"을 바꾸고, 전송·계량 계약과 첫 구현의 기술 범위는 그대로 둔다. 이전의 Builder·Team 플랜(같은 공개 자료에 한도만 다른 구조)은 폐기한다. 그 구조는 "로컬로 무료 복제할 수 있는 자료에 원격 접근만으로 돈을 낼 이유"를 설명하지 못했다.

## 제품과 고객

**하나의 호스팅 자료 서비스에 MCP와 HTTP API 두 입구를 둔다.** 전송 방식마다 별도 상품이나 사용량을 만들지 않는다. 같은 입구가 무료 공개 corpus와 유료 사이트팩을 함께 제공하며, 키의 자격에 따라 사이트팩 검색·조회가 열린다.

무료와 유료를 나누는 기준은 자료의 종류다.

- **무료 = 방법.** 레이아웃 패턴, 레시피, 모션 계약, 용어, 플랫폼 관례, 그리고 `motion/observed-choreography.md`의 관찰 전사 양식. 현재 admitted 169개 전부가 여기에 속하며, 앞으로도 저장소·CLI·stdio MCP·정적 사이트·원격 무료 한도에서 그대로 제공한다. 전사 양식이 무료여야 유료 팩을 읽고 구현할 수 있으므로 양식은 유료로 옮기지 않는다.
- **유료 = 대상.** 특정 실제 웹사이트를 `site-compiler`로 캡처하고 무료 양식대로 전사한 SceneBook(공간 사양)과 SCENEBOOK-TIMELINE(스크롤 초레오그래피 사양), 그리고 빌더 브리프. 무료 패턴의 어휘로 "그 사이트는 어떤 패턴을 어떤 순서·타이밍으로 조합했는가"를 기술한 문서다.

지불 이유의 가설은 사이트팩이 담는 정보가 모델 지식·스크린샷·DOM 덤프로는 얻을 수 없는 종류라는 점이다. 2026-09-21에 확인한 `changeroa/site-compiler`(private, README·SKILL.md·`examples/toss-im/`)의 toss.im 예제는 50,964px 스크롤 스토리를 씬 6개, 초레오그래피 구간 10개, 경계 22개로 나누고 각 경계를 500px 스텝 픽셀 diff로 cut·blend·slide로 판별한다. 같은 저장소의 실측 기록은 같은 Sonnet 급 모델이 산문 브리프로는 재현에 실패했고 SceneBook으로 공간, Timeline 추가로 시간까지 재현했으며, 빌더가 프레임 이미지를 0장 열고 문서만으로 전 씬을 구현했다고 적는다. 이 실측은 도구 작성자 본인이 오케스트레이터로 채점한 것이므로 독립 검증으로 세지 않는다(아래 "출시 전 검증" 참조).

고객 후보는 두 부류다. 첫째, 스크롤 스토리텔링형 사이트를 실제로 납품해야 하는 에이전시·브랜드 사이트 담당자. 현재 대안은 모션 디자이너와 프론트엔드 개발자의 며칠이다. 둘째, 자기 사이트를 리뉴얼하면서 기존 스크롤 연출을 보존해야 하는 팀. 이쪽은 `site-compiler`를 고객 자신의 사이트에 돌리는 서비스이며 관찰 대상이 고객 소유라 저작권 경계 문제가 없다. "토스 느낌의 랜딩"을 원하는 일반 사용자는 고객이 아니다. 그 수준은 모델이 이미 해낸다.

수요가 있다고 확정하지 않는다. “반복 작업이면 반드시 매번 호출한다”, “결정적 검색이므로 원가가 거의 0이다”라는 Fable의 표현은 채택하지 않았다. 캐시나 로컬 복제로 반복 호출이 줄 수 있으며, 모델 호출이 없어도 계산·데이터 전송·인증·회계·지원 비용은 남는다. 현재 원문 검색·읽기·컨텍스트 생성 코드에는 외부 LLM 호출이 필요하지 않다. 사이트팩 생산에는 VLM 전사 호출과 사람 검수가 들어가며, 이것이 팩 원가다.

## 무료·유료 경계와 가격 가설

공통 단위는 **성공한 자료 작업 1회**로 유지한다. search/get/context에 같은 단위를 적용하고, 응답 크기·context 예산은 기존의 명시적 상한으로 제어한다. 원격 무료 한도는 이 단위로 세고, 사이트팩은 작업 수가 아니라 **팩 단위 자격**으로 판다. 아직 가격표를 공개하거나 과금을 활성화하지 않는다.

| 티어 | 자료 | 전송 | 가격·경계 가설 |
| --- | --- | --- | --- |
| 로컬 | 공개 corpus 169개 | 저장소 복제, CLI, stdio MCP, 정적 사이트 | 무료, 영구. 라이선스 파일로 명시해야 성립한다 |
| 원격 무료 | 같은 공개 corpus | 호스팅 MCP·API, 월 1,000 작업 | 무료. 목적은 매출이 아니라 **실패한 검색어와 검색된 사이트 이름**의 수집. 초과 시 중단하고 로컬 접근 안내 |
| 사이트팩 | 사이트 1개의 SceneBook + Timeline + 빌더 브리프 | 같은 호스팅 입구에서 자격 있는 키만 | 팩당 단품. 가격은 대안(모션 디자이너·프론트엔드 며칠)에 견주어 수십만 원대에서 수요 확인. 재컴파일 1회 포함 여부를 조건으로 시험 |
| 카탈로그 구독 | 사이트팩 전체 + 재컴파일 | 같음 | 팩이 20개 이상 쌓인 뒤에만 열 후보. 지금은 만들지 않음 |
| 팀·파일럿 | 고객 자신의 사이트를 `site-compiler`로 컴파일·전사·검수한 팩 + 카탈로그 | 같음 + 고객 전용 비공개 overlay | 프로젝트당 고정 금액. [이전 조사](2026-09-19-monetization.md)의 150만–400만원 가설을 출발점으로 쓰되 견적이 아님 |

사이트팩은 많이 만들 수 없고 그럴 필요도 없다. 스크롤 초레오그래피가 관찰할 가치가 있는 사이트는 한정적이고, 팩 하나에 캡처·VLM 전사 2회·사람 검수가 들어간다. "카탈로그 수백 개"가 아니라 **엄선 20개 안팎**이 상품이다. 원격 무료 한도에서 수집한 사이트 이름 검색 순서가 다음에 만들 팩의 순서다.

이전 문서의 Builder(월 $10–20대)·Team(월 $50–150대) 한도형 플랜은 폐기했다. 좌석·계정·월 한도·가격을 실제 고객 설정으로 구현하지 않는다. 과거 revision 조회, 변경 알림, SLA는 추가 제품 후보이며 현재 제공 기능으로 홍보하지 않는다. 현재 get은 StableRef를 받아 현재 manifest의 자료를 읽으며, 반환된 version_id가 곧 과거 버전 조회 지원을 뜻하지 않는다.

## 전송·계량 계약

MCP 도구와 HTTP API는 기존 네 연산 레지스트리를 호출한다. v2 자료 응답에는 과금 필드를 섞지 않는다. 사용량 상태는 별도 헤더·제품 응답에 둔다. v1 신뢰·적합성 및 A2A/AG-UI는 이 상품의 자료 검색에 합치지 않는다.

| 상황 | 계량 규칙 초안 |
| --- | --- |
| 성공한 search/get/context | 1 unit. 검색 결과 0개도 유효한 성공이면 1 unit |
| discover, 초기화, 도구·자료 목록, ping, 알림 | 0 unit. 남용 방지 요청 제한은 별개 |
| resources/read | get과 같은 1 unit. 도구 대신 resource로 읽어도 한도를 우회하지 않음 |
| 목록 표시명을 얻기 위한 서버 내부 get | 0 unit. 고객 요청과 내부 읽기를 구분 |
| 입력 오류, 인증 실패, 한도 거절, source drift, 내부 실패 | 0 unit |
| 정적 웹 문서 읽기 | 이 계량기 밖. 무료 공개 경로 유지 |
| 일반 응답 캐시 | 새 성공 작업이면 1 unit. 캐시 사용 여부로 고객 단위를 바꾸지 않음 |
| HTTP API에서 명시적 재시도 키로 같은 작업 재전송 | 보존 중인 성공 기록의 키 identity·입력·manifest가 같을 때 재생, 추가 unit 없음. 입력이 달라지면 충돌 |
| 재시도 키 없이 다시 호출 | 새로운 작업. JSON-RPC id를 전역 재시도 키로 오해하지 않음 |
| 응답 도중 연결 해제 | 결과를 성공으로 확정한 뒤라면 사용으로 남을 수 있음. 전달 확인과 정확히 한 번 회계는 같은 문제가 아님 |

월 경계는 UTC 달력월로 고정하고, 작업 시작 시 귀속 월을 정한다. 재시도 보존 기간이 월 경계를 지나더라도 최초 사용을 새 달에 다시 더하지 않는 계약이 필요하다. 실제 유료 운영은 계정별 원자적 예약·확정·취소와 영속 ledger가 있어야 한다. 프로세스 메모리 카운터는 로컬 검증용이며 청구 원장이 아니다. [Cloudflare Rate Limiting](https://developers.cloudflare.com/workers/runtime-apis/bindings/rate-limit/)도 제한용 카운터를 정확한 회계로 사용하지 말라고 명시한다.

첫 prototype의 재시도 보존은 HTTP JSON API의 search/get/context에만 제공하고 기간·개수·저장 바이트를 제한한다. identity별 기록을 분리해 다른 키의 사용이 기록을 밀어내지 못하게 했다. 보존 중인 같은 재시도 키의 입력이나 현재 manifest가 달라지면 새 작업으로 간주하지 않고 충돌로 거절한다. 기간 만료나 용량 정책으로 기록이 사라진 뒤에는 새 작업이다. 큰 성공 응답은 정상 전달·계량하되 저장하지 않을 수 있으며 `Idempotency-Stored: false`일 때 재시도는 새 작업으로 다시 계량된다. MCP와 discover는 재시도 키 헤더를 명시적으로 거절한다. 두 전송의 성공 단위와 월 bucket은 공유하지만 재시도 기능까지 같다고 광고하지 않는다.

로컬 prototype의 계량 주체는 설정한 키의 고정 identity다. 계정·팀 소유권 모델은 아직 없으며, 위의 팀 합산 요금제는 미래 상품 가설이다. HTTP 경로·헤더·오류·재시도 보존 상한의 실행 계약은 구현 디렉터리의 README와 tests에서 확정하고 검증한다.

## 첫 구현의 기술 범위

첫 단계는 **Node 로컬 prototype**이다. 기존 검증된 fs·Git 기반 연산을 재사용하고, 정적 Cloudflare 사이트는 바꾸지 않는다. Worker에 현재 코어를 그대로 import해 배포한다고 가정하지 않는다. 나중에 edge 배포가 필요하면 검증된 immutable snapshot과 별도 reader를 만들고 같은 결과·해시 계약을 다시 검사한다.

중요한 버전 차이가 있다. 설치된 `@modelcontextprotocol/sdk@1.29.0`의 `LATEST_PROTOCOL_VERSION`은 `2025-11-25`다. 현재 공식 [2026-07-28 전송 규격](https://modelcontextprotocol.io/specification/2026-07-28/basic/transports/streamable-http)은 요청별 metadata와 필수 method/name 헤더 등을 정의하는 다른 세대다. 기존 SDK의 stateless 설정을 썼다는 이유로 최신 규격 준수라고 부르지 않는다.

로컬 첫 구현은 설치 SDK가 지원하는 **2025-11-25 계열 Streamable HTTP 호환 prototype**으로 명시한다. 최신 규격은 별도 SDK·클라이언트 전환 검사가 필요한 출시 전 항목이다. [구세대 공식 전송 규격](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)의 Origin 검증·loopback 바인딩과 SDK 응답 처리를 사용한다. 이것은 모든 MCP 클라이언트 호환을 입증하지 않는다.

아래 세 가지를 같은 제품 경계 안에서 구현·검사한다.

1. **HTTP 읽기 adapter:** discover/search/get/context를 기존 코어에 매핑한다. 성공·실패 envelope, UTF-8 범위, StableRef와 admission 경계를 보존한다.
2. **키 식별·shadow usage:** 로컬 환경으로 주입한 테스트 키만 허용하고 헤더에서 읽는다. 키별 한도, 남은 사용량, 실패 비계량, 명시적 재시도 정책을 검증한다. 원문 키·검색문을 로그에 남기지 않는다. 기본 익명 접근과 브라우저 교차 출처 접근은 열지 않는다.
3. **MCP HTTP adapter:** 같은 자료 도구·resource를 제공하며, 내부 목록 읽기와 고객 읽기의 계량 경계를 구분한다. 실제 공식 SDK 클라이언트로 JSON API 결과와 비교한다.

새 디렉터리는 웹 제품의 서버 구현 영역으로 한정하고 npm 공개 package·material admission·v1·기존 stdio에는 과금이나 인증을 삽입하지 않는다. OAuth 발급기, 결제 연동, 영속 회계, 계정 UI, 자동 초과 청구, 외부 배포는 이 로컬 단계에 포함하지 않는다. [현재 MCP 인증 규격](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization)에 맞춘 보호 리소스 discovery와 OAuth 호환은 유료 원격 출시 전에 따로 구현·검증해야 한다.

현재 로컬 코드는 [실행·검증 안내](../server/material-gateway/README.md)에 있다. 독립 검토로 비유한 숫자 입력, 키 간 replay 기록 축출, 무거운 목록 호출 제한을 보완했고, 주 에이전트가 깊은 입력의 재시도 오류도 재현해 깊이 제한을 추가했다. 최종 gateway 검사 18개를 실제 loopback·공식 SDK로 재실행해 통과했다. identity 간 replay 보존과 두 입력 거절도 별도 raw 호출로 확인했다. 구체적 증거와 전체 OKF 검사의 잔여 실패는 [작업 대장](2026-09-19-execution-ledger.md)에 기록한다. 유료 운영 준비 완료라는 뜻은 아니다.

## 운영비 판단

지금 Node prototype의 실측 처리량·CPU·응답 크기·호스팅 공급자 견적은 없다. 따라서 “월 수백만 회도 이 금액이면 충분”이라는 총원가 결론은 내리지 않는다.

대안인 [Cloudflare Workers 공식 요금](https://developers.cloudflare.com/workers/platform/pricing/)은 유료 계정 최소 USD 5/월, 월 요청 1천만 회·CPU 3천만 ms 포함, 초과 각각 USD 0.30/백만 요청·USD 0.02/백만 CPU ms이며 egress 별도 요금이 없다. 아래는 **edge reader를 만들었다고 가정한 계산 예시**일 뿐 현재 Node 코드의 비용 예측이 아니다.

| 월 자료 작업 | 가정한 총 HTTP 요청(1.2배) | 가정한 CPU(요청당 15ms) | Workers 계산 부분만 |
| --- | --- | --- | --- |
| 1,000 | 1,200 | 18,000ms | 계정 최소 $5 안 |
| 100,000 | 120,000 | 1,800,000ms | 계정 최소 $5 안 |
| 1,000,000 | 1,200,000 | 18,000,000ms | 계정 최소 $5 안 |

1.2배와 15ms는 실측하지 않은 가정이며, 기존 계정의 다른 사용량도 포함하지 않았다. 요청당 CPU가 200ms라면 마지막 행은 240M ms로 늘어 계산 부분이 $9.20이 된다. DB·ledger·로그·인증·결제 수수료·지원 인건비·세금·환율은 별도다. 응답 캐시와 정적 읽기를 늘려도 유료 반복 수요가 함께 줄 수 있다. 영업이익이나 총마진은 아직 계산할 근거가 없다.

## 출시 전 검증과 남은 결정

기술 검사는 기존 코어와 HTTP/MCP envelope를 대조하고, 공식 SDK 클라이언트·오류 입력·한도·재시도·동시 요청을 별도로 실행한다. 코어와 결과가 같다는 것은 전송 보존 증거이지 자료 품질이나 사업 효과의 증거가 아니다.

사용 실험은 배포 승인을 받은 뒤 제안할 단계다. 로컬 자료와 동일한 공개 내용에 접근할 수 있게 두고 원격 경로의 설치·첫 유효 결과·반복 작업 편의를 확인한다. 운영자 테스트 키와 재시도 트래픽은 고객 사용에서 제외한다. 키 개수를 고객 수로 환산하지 않는다. “2주 연속 사용 키 10개”와 “상위 한도 요청 3–5건”은 Fable의 탐색 기준이며 수요 입증 기준으로 채택하지 않았다. 가격대를 먼저 제시해 동의를 유도하지 말고 실제 과업·현재 대안·필요 한도를 확인한다. 자발적 요청은 관심 신호, 실제 유료 전환은 별도 신호로 기록한다.

사이트팩의 검증 순서는 다음과 같다. 싸고 빠른 것부터 하며, 앞 단계가 실패하면 뒤 단계를 만들지 않는다.

1. **라이선스.** 최상위 LICENSE 파일과 root package.json의 license 필드가 없다(2026-09-19 확인, 2026-09-21 현재 동일). 이것이 없으면 "로컬 무료"조차 성립하지 않는다. 문서와 코드의 조건은 소유자 결정이다.
2. **팩 1개는 이미 있다.** toss.im 예제(2026-09-10 캡처)가 첫 팩이다. 새로 만들지 않고 이것을 판매판 조건(원문 카피 제거, 갭 검수)에 맞게 다듬는다.
3. **효능의 독립 검증.** 같은 모델·같은 시간 한도로 "toss.im 같은 스크롤 스토리 페이지" 과업을 팩 없이(산문 브리프)와 팩으로 각각 새 세션에서 구현한다. 결과물 두 개를 조건 이름을 가린 채 이해관계 없는 사람 여러 명에게 보여주고 어느 쪽이 원본에 가깝고 더 잘 만들어졌는지 고르게 한다. `site-compiler` 저장소의 v2·v3 실측은 이 비교에 가깝지만 채점자가 도구 작성자라 대체하지 못한다. 팩 쪽이 뚜렷이 이기지 못하면 상품이 아니다. 이기면 그 결과물이 랜딩페이지이자 가격 근거다.
4. **원격 무료를 초청제로 열기.** gateway 로컬 prototype은 있다. 초청한 사용자만 쓰게 하고, 사용자 수가 아니라 실패한 검색어와 검색된 사이트 이름을 본다.
5. **팩 5개까지 만들고 단품 판매.** 4에서 나온 사이트 이름 순서대로 만든다. 미리 채우지 않는다.
6. **팀·파일럿 1건.** 고객 자신의 사이트를 컴파일하는 서비스는 3과 병행해 제안할 수 있다. 저작권 경계가 없고 첫 입금이 나올 가능성이 가장 높은 경로다.
7. 여기까지 신호가 있을 때 OAuth·영속 ledger·결제를 붙인다. 수요 확인 전에는 만들지 않는다.

남은 소유자 결정은 공개 배포·라이선스 정리, 판매 주체와 결제 제공자, 외부 공개 시험의 운영 한도, 사이트팩 저장 위치, 그리고 관찰 대상 사이트의 상표·저작권 취급에 대한 법률 검토다. 이 결정을 대신하거나 새 계정을 만들지 않았다. 제품 방향인 MCP·API는 재선택 대상이 아니라 이 결정들의 전제다.
